# Adopt an existing application

Arguments: `$ARGUMENTS`. CLI: `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/appforge.py" metamodel …`.
Work on a branch (`feat/metamodel`) and never touch `.env*`.

## 1. Database to read
The local Supabase of the app is the usual source: `supabase start` then
`postgresql://postgres:postgres@127.0.0.1:54322/postgres` (ask the user to start it if it is not running; never
use a production database without explicit permission). Alternatively apply the migrations to a scratch
PostgreSQL.

## 2. Reverse engineering
`metamodel reverse --db <DSN> --package <name> -o domain.ecore.yaml` (use `--exclude` for infrastructure
tables of the app, `--include` to limit the scope). Then review it **with the user**:
- class and feature names (rename freely: `column:` keeps the link to the database column);
- containments inferred from `on delete cascade`, many-to-many from join tables, enums from `check (… in …)`;
- `language: it` if the names are Italian; `doc`/`label` for the main classes;
- columns reported as "not described" (e.g. `state` of a hand-written workflow) — describe the workflow in
  words in the report; it is not part of the metamodel of an adopted app.
Validate (`metamodel validate`) and check alignment (`metamodel drift --db <DSN>` → "aligned").

## 3. Web modeler in the admin area
`metamodel install-modeler <app>` copies:
- `public/appforge/metamodel-editor.js` (the framework-free editor),
- `src/components/appforge/metamodel-modeler.tsx` (React wrapper),
- `src/lib/appforge/metamodel-actions.ts` (server action saving proposals),
- `src/lib/appforge/metamodel.json` (the metamodel read by the page),
- `supabase/migrations/<ts>_model_change_requests.sql` (proposals stored in production).
Then adapt them to the app (read its CLAUDE.md and admin pages first):
- in `metamodel-actions.ts` replace `requireRole("admin")` and the Supabase client import with the app's own
  admin check and server client;
- in the SQL, replace `public.is_admin()` with the app's admin predicate;
- create the admin page (e.g. `src/app/(admin)/admin/model/page.tsx`) following the app's layout: it renders
  `<MetamodelModeler metamodel={metamodel} canEdit lang={locale} onSave={saveMetamodelProposal} />`;
- add the link to the admin navigation and the labels to the app's translations.
Run the app's typecheck, lint and tests.

## 4. Keeping them aligned
- Every schema change is made in the metamodel **and** in a migration in the same change; the appforge hook
  reminds it when a migration is edited.
- `metamodel sync` refreshes `metamodel.json` after the metamodel changes; `metamodel drift --db <DSN>` must
  report "aligned". With `APPFORGE_DRIFT_DB=<DSN>` in the environment the session start reports drift too.
- Proposals made by admins in production: `metamodel pull --db <DSN>` then `/appforge:metamodel apply`.
- Suggest a CI step that applies the migrations to a scratch database and runs `metamodel drift`.
- Hand-written logic the metamodel does not express (custom workflows, business rules, special pages) is a
  customization: list it in `docs/customizations.md` (id, why the model is not enough, model elements involved,
  files, how it is verified) and mark the code with `CUSTOM(<id>)`; confirm the list with the user.
- Add to the app's CLAUDE.md: "The domain metamodel is domain.ecore.yaml: change it with /appforge:metamodel
  together with the migration; check with `metamodel drift`."

## 5. Later: generation
An adopted app can move to generation only by rebuilding it from the metamodel (`/appforge:new-app` with this
metamodel plus an `app.yaml` for its behaviour) and migrating the data: discuss it as a separate project.
