# modeler

Model-based development of Next.js + Supabase apps driven by a **domain metamodel** in Ecore notation
(`domain.ecore.yaml`), with a **web modeler that becomes part of the application**.

- The metamodel is the source of truth of the domain structure: classes, attributes, references
  (multiplicity, containment, opposite), enums, inheritance, and the domain `rules` the structure cannot express
  (`{id, text}` on the package or a class). It is written from the prompt (`/modeler:metamodel`) or derived from
  the app's database (`reverse`).
- `/modeler:install` puts the modeler in the app's repository: editor (`public/modeler/`), React wrapper,
  server action that saves proposals, admin page `/admin/model`, table `model_change_requests`, and the CLI
  itself in `tools/modeler/` with `npm run model:*` scripts. After that the app does not need the plugin:
  `model:validate`, `model:sync`, `model:docs`, `model:behavior`, `model:engine`, `model:migrate`, `model:drift`,
  `model:proposals`, `model:pull`, `model:apply`, `model:done` run from the repository and in CI.
- `docs/DOMAIN.md` is the domain explained, generated by `sync` from the metamodel (package, Mermaid diagram, one
  section per class with attributes, references and rules, enums) and also an inbox: details, constraints and rules
  written there by hand are detected by `docs` (section by section, formatter changes ignored) and reported at
  session start; `/modeler:metamodel` translates them into the metamodel (structure or `rules`), then
  `sync --force` regenerates the file (the original goes to `.modeler/backups/`). `sync` never overwrites hand edits;
  it keeps a copy of what it wrote in `.modeler/DOMAIN.generated.md`, so hand edits are told apart from metamodel changes.
  A `docs/domain.md` with other letter case (appforge apps) is another document: nothing is written until it is
  renamed or removed (`docs` and the session hook say so).
- `migrate` drafts the SQL migration from the previous metamodel (committed `HEAD` by default) to the current one:
  tables, columns, foreign keys, join tables, enum literals and renames are written; RLS policies, backfills and
  anything that loses data are left as commented `TODO(modeler)` lines to resolve.
- A save in the modeler never changes the running app: it is a **proposal** (a file in `.modeler/proposals/` in
  development, a `model_change_requests` row in production) applied with `/modeler:apply`, which goes on with
  the migration and the code in the same change. Until then `/admin/model` lists it above the editor (date,
  author, note, the changes as `modeler diff` prints them), where it can be opened or rejected, and the session
  start reminds the developer of the proposals in `.modeler/proposals/`.
- `drift` compares the metamodel with a live database (local Supabase by default): "aligned" is the invariant.
- Behaviour is the second model, **`behavior.yaml`** next to the metamodel: roles, derivations of the attributes
  marked `derived: true`, workflows (states, transitions, guards, timed transitions), events, reactions (who is
  notified when) and webhook subscriptions, written on the metamodel's concepts with typed expressions
  (`guard: dataComplete`, `when: reason.compensationType = hourly and hours > 0`, `notify: [director, self.issuer]`).
  `validate` checks it against the metamodel, the hook does it after every edit of either file (a domain change
  that breaks a guard, a recipient or a derivation is reported at once), `apply` reports a proposal that breaks
  it. `sync` generates `docs/BEHAVIOR.md` (state diagrams, tables of states, transitions, derivations, reactions)
  and `src/lib/modeler/behavior.json` (every expression typed, with its SQL); `model:behavior -- --format sql`
  prints derivations and guards as PostgreSQL, `--format engine` the workflow versions as the runtime engine
  stores them (clauses, principals, timed triggers); `drift` compares the workflows with the versions published in
  the database. In the web modeler, when the page passes `behavior.json` (`install` says so while it does not),
  the diagram shows the behaviour next to the structure: a class with a workflow has a «workflow» head and,
  when selected, its **state diagram in a panel under the canvas** (laid out at the panel's width with the real
  text widths: states in their colour, transitions in the colour of the target, timed ones dashed, final sinks on a
  bus, hover highlight; the panel follows the selection, so the domain diagram stays clean; the same diagram is
  reusable on the app's pages: `<WorkflowView behavior entity state>` of `workflow-view.tsx` wraps the
  `<workflow-view>` element of the same kit file and shows the workflow of a record with its current state filled
  with its colour, the transitions leaving it at full strength and the others dimmed, laid out at the width of its
  container), derived
  attributes are marked `/name` with the formula in the tooltip and in the panel, the state attribute `⟳`, and the
  features the behaviour uses (formulas, guards, principals, recipients, role scopes: the `uses` map of
  `behavior.json`) carry ` ·ƒ` with "used by" in the tooltip, a class without a workflow but involved has `ƒ` in its
  head; a legend tells the three levels apart (workflow, involved, structure only). Under the diagram the
  behaviour is listed (roles, workflows, derivations, classes involved, events, reactions), following the class
  selected, and edited: states, transitions, revert, formulas, events, roles and reactions; a save is a proposal
  with metamodel and behaviour, and `apply` writes `behavior.yaml` as well (validated against the proposed
  metamodel, backed up, comments listed). `model:engine -- --write` generates the SQL engine itself as one idempotent migration: derived
  attributes computed by triggers (and refreshed when the rows they navigate to change), `<entity>_perform_transition`
  with principals, conditions, guards, comments, history and events with the recipients of the reactions,
  `_available_transitions`, `_revert`, `_run_timed_transitions`, `_run_reminders`, lifecycle events; it relies on
  the app's `current_profile_id`, `has_role`, `role_members`, `emit_entity_event` (fallbacks where missing). What
  neither model expresses is a customization listed in `docs/customizations.md` and marked `CUSTOM(<id>)`.

## Install
From the harness clone: `./install.sh` (installs `core` and `modeler`). From GitHub:

    /plugin install modeler --marketplace iovinoludovico/iovino-harness

## Commands (skills)
| Command | What it does |
|---|---|
| `/modeler:install [app] [DSN]` | metamodel from the database if missing, modeler and CLI in the app (re-run to upgrade) |
| `/modeler:metamodel <description> \| show` | metamodel from natural language, then migration, code, drift |
| `/modeler:apply [proposal] \| pull [DSN]` | applies the proposals saved by the modeler |

Knowledge skill loaded automatically: `notation` (syntax of both models, storage mapping, ambiguities to settle).

Hooks: validate `domain.ecore.yaml` after every edit, and `behavior.yaml` against it when either changes
(PostToolUse, errors go back to Claude); remind to update
the metamodel when a migration changes; at session start describe the app's metamodel, report a vendored
modeler older than the plugin and, with `MODELER_DRIFT_DB`, the drift from the database.

## CLI
```bash
python3 scripts/modeler.py validate tests/fixtures/anagrafica.ecore.yaml
python3 scripts/modeler.py validate tests/fixtures/invitations.ecore.yaml --behavior tests/fixtures/invitations.behavior.yaml
python3 scripts/modeler.py behavior tests/fixtures/invitations.ecore.yaml --behavior tests/fixtures/invitations.behavior.yaml --format sql
python3 scripts/modeler.py engine tests/fixtures/invitations.ecore.yaml --behavior tests/fixtures/invitations.behavior.yaml   # the SQL engine
python3 scripts/modeler.py show tests/fixtures/anagrafica.ecore.yaml --format storage   # emfatic|mermaid|markdown|json|yaml
python3 scripts/modeler.py reverse --db postgresql://postgres:postgres@127.0.0.1:54322/postgres -o domain.ecore.yaml
python3 scripts/modeler.py install ~/code/my-app
# inside the app
npm run model:validate && npm run model:sync
npm run model:migrate                                # preview the migration draft (from HEAD)
npm run model:migrate -- --name add_phone --write    # save it in supabase/migrations/, then resolve TODO(modeler)
npm run model:drift
```
`drift` also compares the workflows of `behavior.yaml` with the versions published in the database (tables
`workflow_versions`/`workflow_states`/`workflow_transitions`; an app without them gets a note).
`drift`/`reverse` use `--db`, else `MODELER_DB`, else the local Supabase port in `supabase/config.toml`;
`MODELER_EXCLUDE` lists the app's infrastructure tables to ignore, and `table.column` for a single technical
column (e.g. a foreign key to an excluded table). `export`/`import` exchange `.ecore` XMI with
Eclipse EMF and Epsilon.

## Requirements
Python 3.10+ (PyYAML if installed, else the vendored pure-Python copy in `scripts/vendor`); `psql` for
`reverse`, `drift`, `pull` and `done`. `pull` and `done` connect to the Supabase project linked with
`supabase link` (or `MODELER_PROD_DB`, or `--db`); psql takes the password from `SUPABASE_DB_PASSWORD` or `~/.pgpass`, or asks for it in a real terminal (not from
Claude Code: its tools and `! …` commands have none, and the CLI then stops with the `~/.pgpass` line to add).
